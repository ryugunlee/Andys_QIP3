# 작업 중 결정사항
코딩 작업 중 주요하거나 다시 찾아보게 될 수도 있는 방향상의 결정사항을 여기에 적고, 그렇게 결정한 이유와 아이디어 등 배경을 작성한다.
AI가 선택지로 제시하여 결정한 이력들도 여기에 남아, 다시 사용된다.
결정 사항이 충돌하는 명령을 하게 될 경우, 참고 자료로서 보여주며 결정 사항에 대해 다시 질문한다.


## AI가 했던 설계 관련 질문 및 결정사항.
클로드 코드가 질문하여 답변한 것들은 여기에 작성된다.

### (2026-09-07) QIP4 정량 규칙 체계 신설 — QIP3와 병행, 수집 계층까지 확장

`.claude/투자 규칙.md`에 새로 작성된 정량 규칙(안정성 관문 → 성장·가치 점수 → 효율성 승수 →
모멘텀 집행률)의 구현 가능성을 실제 API 호출로 감사한 뒤, 사용자 결정으로 착수.

질문하여 답변받은 결정:
- **QIP3를 대체하지 않고 QIP4로 병행 추가** (QIP3 신설 전례와 동일).
- **데이터가 막히면 수집 시스템을 고쳐서 해결한다** — 미국 분기 재무제표 수집, 컨센서스
  관측일 이력, 한국 업종명 매핑을 새로 만든다.
- 그래도 자동 수집이 불가능한 항목은 **정성 평가로 이관**하고 규칙 문서에 사유를 남긴다.
- **상대강도 기준점 = 자체 산출 시가총액 가중 지수.** 주식수는 각 수집 run의
  `Market Cap / Close`로 역산해 다음 run까지의 일봉에 적용한다(look-ahead 없음).
  시장·섹터·산업 3단계 전부 산출.
- **12분기 성장 연속성은 하이브리드 자동 승격**: 가용 분기가 16개 미만이면 연간 4개년으로
  판정하고, 누적되어 16분기가 차면 자동으로 원 규칙(12분기)으로 전환. 사용한 기준을
  컬럼에 기록해 화면에 노출한다.
- **안정성 관문 탈락 사유를 상세 페이지에 항목별로 표시한다** — 기존 QIP3는 탈락 사유를
  전혀 보여주지 않고 생존 종목만 노출했다. "판단을 돕는 자료를 충분히 제공한다"는
  프로그램 목표에 맞춰 신규 UI 컴포넌트를 만든다.
- `투자 규칙.md`의 **정량 파트를 전면 재작성**한다(경계조건·시장별 정의 차이·미구현 사유 명시).
- `_qip3_section.html`이 복제하고 있는 카드 마크업을 **공통 partial로 파라미터화**한 뒤
  QIP4를 얹는다(세 번째 복제본 방지).

설계 판단:
- **다년 계산은 `collection/`, 임계값 판정은 `analysis/`.** `analysis/`는 100% 횡단면이라
  다년 시계열을 다룰 수 없다(선례: `financial_trend.evaluate_uptrend`). 반대로 임계값 판정을
  `analysis/`에 두면 **규칙이 바뀌어도 재수집(수 시간) 없이 재채점(수 초)만 하면 된다.**
- **탈락은 Boolean이 아니라 승수 0.0으로 표현한다.** 이 저장소에는 컴포지트에 곱셈을 적용하는
  코드가 하나도 없었는데, 탈락을 숫자로 두면 `analysis/`는 여전히 "연속값 곱"만 하게 되어
  새 규약을 만들지 않아도 된다. 최종 컷은 종전처럼 `storage/qip4_selection.py`가 맡는다.
- **한국 `sector`/`industry`는 종전처럼 같은 값을 유지**하고 라벨만 숫자→한글로 바꾼다.
  그룹 분할이 동일하므로 기존 섹터/산업 점수의 수치는 변하지 않는다.

원 규칙에서 축소·대체한 정의(데이터 한계):
- 조정 순부채: 계열사 지급보증·CB/BW/RCPS·특수관계자 대여금이 **주석 전용**이라 수집 불가 →
  관측 가능한 항목만으로 축소하고 **KR/US 정의를 분리**한다. yfinance `Total Debt`에는
  리스부채가 이미 포함되어 있어(실측 확인) 미국은 별도 가산하면 이중계상이 된다.
- 실질 자기자본: 자산화된 개발비·특수관계자 대여금 분리 불가 → 영업권·이연법인세자산만 차감.
  차감 항목이 줄어든 만큼 **임계값을 0.6 → 0.75로 상향**해 원 규칙의 엄격도를 보존한다.
- 주주환원수익률: 자사주 **소각**은 취득과 구분되지 않음 → 순자사주매입 기준으로 정의 변경.
- 재고 경보 해제: 수주잔고는 사업보고서 본문에만 있어 수집 불가 → **선수금 증가**로 대체
  (수주잔고 증가의 실질 대리 변수이고 실제로 API에 있다). 미국은 해제 불가.
- 이익 모멘텀: 영업이익 대신 **EPS 컨센서스 리비전**. 미국은 `eps_trend`가 90일 전 값을 직접
  주어 즉시 가능하고, 한국은 관측일 이력을 쌓아야 해 3개월 뒤부터 산출된다.
  **적자 기업은 분모가 작은 음수라 비율이 폭주하므로(실측 -133%) 산출에서 제외한다.**

### (2026-07-19) 매출·영업이익 5년 오름세 판정(Y/N) 추가 — 판단 기준을 AI가 설계
사용자가 "5년 전 대비 매출·영업이익이 꾸준히 올랐는지, 1~2년 정도 허우적거림은 괜찮지만
5년간 오름세가 확실한지를 Y/N으로 평가해달라"고 요청. 질문 없이 판정 규칙을 직접 설계했다
(별도 확인 없이 진행 — 리스크가 낮고 되돌리기 쉬운 판단이라 판단):

- **판정 로직**(`collection/financial_trend.py`): (1) 마지막 해 값이 첫 해보다 커야 함(순증가,
  영업이익은 적자에서 시작해도 무방 — 절대 수준이 아니라 방향만 봄) (2) 전년 대비 하락한 해의
  수가 허용치 이하. 허용치는 **가용 연간 기간 수에 비례**: 5개년(YoY 비교 4회) 이상이면 하락
  2년까지, 4개년(비교 3회)이면 1년까지 허용. 최소 4개년 미만이면 판정을 보류하고 None(결측).
- **데이터 소스 제약이 판정 설계를 좌우함**: 로컬 DB로 확인한 결과 네이버(WiseFn)는 5개년
  실적을 주지만 yfinance 무료 엔드포인트는 보통 4개년만 준다(PROBLEMS #23). "5년"이라는
  표현을 문자 그대로 강제하면 미국 종목 다수가 항상 판정 불가능해지므로, 위처럼 가용 기간에
  따라 규칙을 조정해 두 소스 모두 판정 가능하게 했다 — 이 사실을 QUANT.md에도 명시.
- **저장 위치**: percentile/standard 스코어링 대상이 아닌 Y/N 텍스트 플래그로, 기존
  `Value risk`/`Growth risk` O/X 패턴과 동일하게 처리(curated 컬럼 + `presentation/metrics.py`
  TEXT 표시). **QIP3 성장성 요인의 가중치·수식에는 연결하지 않았다** — 사용자가 "평가하게
  하자"고 한 것은 새 판정 지표 자체의 추가였고, 기존에 튜닝된 QIP3 가중치를 별도 지시 없이
  바꾸는 것은 범위 밖이라 판단했다. 향후 하드 필터/가중치로 편입하고 싶다면 재논의 필요.

### (2026-07-19) QIP3 5요인 점수 체계 신설 — 기존 체계와 병행
사용자가 "가지고 있는 지표 중 규모 무관 비율형 지표로 다시 점수를 매겨, 안정성/재무건전성/
성장성/가치성/모멘텀 5요인을 0~100으로 채점하고, 안정성 하위 20%는 무조건 제외한 뒤 가치·성장·
모멘텀 우선·재무건전성 부차로 시장별 약 10%를 선별하라"고 요청. 방법론·근거는 `QUANT2.md`에 저장.

질문하여 답변받은 결정:
- **선별 범위 = 시장별 10%** (KOSPI/KOSDAQ/NASDAQ/NYSE 각각). 회계기준·통화 차이로 시장 간
  직접 비교가 부적절(PROBLEMS #9)해 run(=시장) 단위가 자연스럽다.
- **시장 전체 점수와 섹터 내 점수 둘 다 산출** + 선별 결과의 섹터/시장 쏠림을 화면에 표시.
  기존 파이프라인이 이미 전체/Sec/Ind 3모집단을 지원해 그대로 재사용(`QIP3 Score`/`…Sec`/`…Ind`).
- **이번에 사이트까지 반영**. 단, 로컬은 소형 픽스처 DB뿐이라 docs는 커밋하지 않고
  `deploy-site.yml`이 실데이터로 재빌드하게 둔다.

설계 판단(근거는 QUANT2.md):
- 종합 가중치 가치0.35/성장0.25/모멘텀0.25/건전성0.15. **안정성은 종합에 넣지 않고 하드 필터 전용**
  (Greenblatt식 2단 선별).
- 가치는 O'Shaughnessy Value Composite(6지표 동일가중). **PFCR 제외**(FCF 부호 문제 #32) → PCR 사용,
  **PEGR 제외**(가치·성장 이중계상).
- **유효법인세율은 컴포지트 제외**(이월결손금·일회성 세액공제로 극단값이 부실 신호일 수 있음) —
  화면·섹터 비교용으로만 채점.
- 순부채비율·설비투자비율은 음수/0 정상값이라 RECIPROCAL 대신 **NEGATED** 방향.
- **금융 섹터 레버리지 왜곡**은 한국 Sector가 숫자 업종코드(#20)라 이름 예외가 불가 →
  안정성 필터를 `0.5×시장전체 + 0.5×섹터내` 블렌드로 완화.
- DECISIONS(2026-07-18)에서 "다음 단계"로 남겼던 신규 재무 팩터 10종의 방향성·가중치를 이번에
  재무건전성/안정성 요인으로 연결. `snapshot_factors`에 QIP3 점수 컬럼 약 130개 추가(동적 스키마 수용).

### (2026-07-18) 수집 매크로는 표현 계층 재빌드까지 책임진다 — 6개 워크플로 전부 통일
사용자가 표현 영역과 배포 사이트의 연결 원칙을 명확히 했다: **(1) 정보를 가져오는 매크로는
수집만 하는 게 아니라 표현 영역 재빌드(사이트 반영)까지 해야 하고, (2) 표현 계층 코드를
바꿔 push하면 배포된 GitHub Pages에도 반드시 그 변경이 보여야 한다.**

점검 결과:
- (2)는 이미 보장됨 — `deploy-site.yml`이 `presentation/**`·`build_site.py` push마다
  전체 DuckDB 복원 → `build_site.py` 재빌드 → `docs/` 커밋을 수행하고, GitHub Pages가
  main/docs를 서빙한다. 빈 데이터로 사이트를 지우던 과거 사고는 `EmptySiteError`
  가드로 이미 해결(PROBLEMS #26).
- (1)은 6개 수집 워크플로 중 `collect-macro.yml`만 재빌드를 안 하고 있었다(PROBLEMS #31).
  사용자 지시("안 되어 있으면 만들라")에 따라 나머지와 동일하게 수집 직후
  `build_and_commit_site.sh`를 실행하도록 맞췄다. build_site가 주식 DB도 읽으므로 복원
  범위를 전체(`*.duckdb`)로 넓혔다. 이제 6개 전부 표현 계층까지 갱신한다.

### (2026-07-18) 홈/주식 분석 페이지 뉴스 = Google News RSS("세계 경제") + 연합뉴스 경제 RSS 병합
"홈에서 세계 경제 관련 뉴스 기사 링크와 헤드라인을 수집해 올 수 있을까?"라는 요청에 대해, 이미
설계돼 있던 뉴스 연결 지점(`presentation/models.py`의 `NewsItem`, `news_provider.py`의
`load_news()` placeholder, `_news_section.html`)을 실제로 채우는 작업으로 진행했다.

소스 결정 과정에서 두 가지를 질문하고 답변받았다:
- **소스**: Google News RSS(`news.google.com/rss/search?q=세계+경제&hl=ko&gl=KR&ceid=KR:ko`) +
  연합뉴스 경제 RSS(`yna.co.kr/rss/economy.xml`) 둘 다 병합하기로 결정(다양성 우선, 중복은
  url 기준 제거).
- **Google News RSS 이용약관 리스크**: 실제로 받아보니 저작권 문구가 "개인용 피드리더,
  비상업적 용도로만 사용 가능, 그 외 용도는 명시적으로 금지"였다. 이 프로젝트는 공개
  웹사이트라 문면상 이 범위를 벗어난다는 점을 알렸고, 개발자가 **"그대로 포함"**을 택해
  리스크를 인지한 상태로 진행했다. 헤드라인+링크(+연합뉴스 쪽만 짧은 요약)만 저장하고 본문은
  저장하지 않는 애그리게이터 방식으로 제한했다.
- **자동화**: 매크로 워크플로(`collect-macro.yml`)처럼 매일 GitHub Actions로 수집한다
  (`collect-news.yml`, 22:30 UTC — 같은 macro DB 자산을 다루는 collect-macro.yml 23:30 UTC와
  1시간 간격을 둬 `--clobber` 업로드 경합을 피함). 뉴스는 홈에 바로 반영돼야 하므로, 매크로와
  달리 이 워크플로는 수집 직후 `build_and_commit_site.sh`까지 실행해 사이트도 재빌드한다.
- **노출 개수**: "주요 기사 5개(요약 포함) + 헤드라인만 20개"로 답변받아 2단 레이아웃으로
  구현했다(`presentation/config.py`의 `NEWS_FEATURED_LIMIT`/`NEWS_LIST_LIMIT`).

구현 중 발견한 문제: 연합뉴스 경제 RSS는 게시 빈도가 훨씬 높아(하루 수십 건), 단순 발행일
최신순으로 두 소스를 병합하면 "주요 5개" 자리가 국내 일반 경제 기사(부동산·소송 등)로
채워지고 정작 "세계 경제" 검색 결과(Google News)가 밀려나는 것을 로컬 테스트로 확인했다.
그래서 수집 시점에 `origin`(google_news/yonhap) 태그를 붙이고, 표현 계층
(`news_provider.py`)에서 주요 5개는 Google News를 우선 채우고 부족분만 최신순으로 채우도록
했다 — 그 아래 헤드라인 20개는 원래대로 최신순 병합이라 다양성은 유지된다.

구현 파일: `collection/news/`(constants/parsers/google_news_source/yonhap_source),
`storage/news_repository.py` + `storage/database.py`의 `news` 테이블, `collect_news.py`

### (2026-07-17) 모바일 앱 = Flutter가 아니라 PWA. 표현 계층 언어는 TypeScript 유지
"Flutter로 모바일 앱을 만들고, 웹에 설치 링크를 보여 달라"는 요청에 대해 **PWA(홈 화면에 추가)**로
결정했다. Flutter/Dart는 도입하지 않는다.

그렇게 정한 이유:
- **iOS 설치 링크는 Flutter로도 불가능하다.** 아이폰은 App Store/TestFlight를 거치지 않고 설치할
  방법이 없고 둘 다 Apple Developer Program(연 $99)과 심사가 필요하다. 즉 요청의 핵심인
  "웹 들어가서 링크로 설치"를 Flutter는 안드로이드에서만, PWA는 iOS·안드로이드 양쪽에서 달성한다.
  목적 자체를 PWA가 더 정확히 만족한다.
- 안드로이드 APK 직접 배포도 "출처를 알 수 없는 앱" 허용·Play Protect 경고라는 마찰이 있고,
  스토어 등록은 비용·심사·신원확인이 따른다.
- 백엔드 서버가 없어 앱을 만들어도 결국 GitHub Pages의 정적 JSON을 읽는 구조가 된다. 그러면
  웹과 정보 신선도가 같으므로 네이티브의 이점이 크지 않다.
- **CLAUDE.md "데이터 표현 영역은 TypeScript 예정"과 Dart가 충돌**한다. 이 충돌을 질문했고,
  개발자가 "TypeScript 유지(PWA)"를 택했다. 표현 계층 언어를 Python(Jinja)+TS+Dart 셋으로
  늘리지 않는다.

이 선택의 큰 이점: PWA는 **사이트 자체가 앱**이라 앱 전용 코드도, 앱용 JSON API도 없다. 그래서
"앱이 다룰 데이터 범위 = 웹과 동일 전부"(질문에 대한 개발자 답변)가 추가 작업 없이 자동 충족되고,
표현 계층을 고치면 설치된 앱도 그대로 따라 바뀐다. 유지보수 대상이 하나로 유지된다.

한계(알고 선택한 것): 푸시 알림(iOS 제약 큼)·스토어 노출·네이티브 성능은 포기한다. 나중에 이것들이
정말 필요해지면 그때 다시 판단한다 — PWA를 넣었다고 앱 개발이 막히지는 않는다.

구현은 `presentation/builders/pwa.py` + `templates/{manifest.webmanifest,sw.js}.jinja` +
`static/{install,sw-register}.js` (STRUCTURE.md 참고).

### (2026-07-17) docs 재배포 워크플로 트리거 = 수동 + presentation 변경 시 자동
표현 계층만 바꿔도(데이터 재수집 없이) 사이트가 갱신되도록 독립 워크플로

### (2026-07-17) 빈 사이트는 산출물이 아니라 실패로 다룬다
`build_site.py`가 데이터 0건일 때 경고만 남기고 빈 사이트를 만들어 CI가 배포본을
덮어쓴 사고(PROBLEMS #26)를 겪고, "데이터가 없으면 빈 사이트를 만드는" 동작 자체를
버그로 판단했다. `EmptySiteError`로 중단하고 종료코드 1로 끝낸다. 대안으로 "CI에서만
커밋을 막는" 방법도 있었으나, 잘못된 산출물을 만든 뒤 거르는 것보다 **애초에 만들지
않는 쪽**이 옳다고 보아 표현 계층 자체에 가드를 넣었다. 부작용: 데이터 없이 사이트
미리보기를 만들 수는 없게 됐다 — 필요해지면 명시적 플래그(`--allow-empty` 등)를 추가한다.

### (2026-07-17) CI 데이터 공급은 data-store 릴리스 씨앗으로 해결 (docs 중심 리팩터링은 기각)
사용자가 "docs를 중심으로 표현 영역을 리팩터링"하는 선택지를 제시했으나, `docs/`는
`presentation/`이 만드는 **생성 산출물**이지 소스가 아니므로 방향이 뒤집힌다고 판단해
현 구조(`presentation/` → `build_site.py` → `docs/`)를 유지하기로 합의했다. 실제 고장은
구조가 아니라 **CI의 데이터 공급 부재**였고, 로컬 DuckDB 3종을 `save_db.sh`로
`data-store` draft 릴리스에 올려 씨앗을 심는 것으로 해결했다. 이후로는 수집 워크플로가
그 위에 누적한다.

### (2026-07-17) 전체 시장 수동 수집은 하지 않고 스케줄(월·화·수·목)에 맡긴다

### (2026-07-18) 재무 팩터 10종을 수집 영역에만 추가 (스코어링 미연결)
