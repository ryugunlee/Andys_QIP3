# 작업 중 결정사항
코딩 작업 중 주요하거나 다시 찾아보게 될 수도 있는 방향상의 결정사항을 여기에 적고, 그렇게 결정한 이유와 아이디어 등 배경을 작성한다.
AI가 선택지로 제시하여 결정한 이력들도 여기에 남아, 다시 사용된다.
결정 사항이 충돌하는 명령을 하게 될 경우, 참고 자료로서 보여주며 결정 사항에 대해 다시 질문한다.


## AI가 했던 설계 관련 질문 및 결정사항.
클로드 코드가 질문하여 답변한 것들은 여기에 작성된다.

### (2026-09-16) 정성 평가 웹 실행 — PFmanager Supabase 계정 공유, 권한 3단계, Actions가 실행기

"정성 평가를 웹에서도 안전하게 실행하고 싶다. 관리자 로그인이 필요하고, PFmanager 계정을 연동하고
싶다"는 요청. QIP3 사이트는 GitHub Pages의 정적 파일이라 서버가 없으므로 **Actions를 원격 실행기로
쓰고, 그 앞에 Supabase를 권한·비밀 계층으로 세우는** 구조로 정했다. 질문해 정한 것:

- **Supabase 프로젝트는 PFmanager와 공유한다.** 계정 저장소(`auth.users`)가 하나여야 이메일·비밀번호가
  실제로 같아진다. `admins`·`allowed_emails`·`is_admin()`을 그대로 재사용하고, QIP3가 만드는 것은 전부
  `qip_` 접두사를 붙여 섞이지 않게 했다. 전용 프로젝트를 새로 파는 안은 "연동"이 이뤄지지 않아 기각.
- **실행 권한은 관리자 / deep 허가자 / quick 허가자 3단계.** 개발자 지시("누군가는 quick만, 누군가는
  deep도 쓸 수 있게"). `qip_permissions`를 **email 키**로 두어 상대가 가입하기 전에도 권한을 줄 수 있게
  했다(PFmanager의 allowed_emails와 같은 방식). 일일 상한은 행마다 다르게 주고, **관리자는 상한 없음**
  (개발자 선택 — "내가 내 돈을 쓰는 건 내 자유"). 기본값은 quick 5건·deep 3건.
- **상한을 지키는 주체는 DB다.** jobs 테이블의 INSERT 정책이 `qip_can_request(tier)`를 호출하므로,
  화면이나 Edge Function을 뚫어도 권한 밖 행은 만들어지지 않는다. 함수의 사전 검사는 사람에게 이유를
  설명하기 위한 것(403/429 메시지)이지 방어선이 아니다.
- **AI 키를 CI에 올리는 것을 허가받았다 — 단, 새 워크플로 하나에만.** 2026-09-16의 "워크플로에 AI 키를
  넣을 경로 자체를 없앴다"를 뒤집는 사안이라 명시적으로 물었고, 폭발 반경을 `qualitative-run.yml`
  하나로 한정하는 조건으로 진행했다. 정기 실행(`qualitative-weekly.yml`)은 무과금 경로로 그대로 둔다.
- **publishable 키를 docs에 커밋하는 것을 허가받았다.** Pages가 main/docs를 서빙하는 이상 브라우저에
  내려가는 것은 전부 git에 있어야 한다. 이 키는 공개 전제 값이고 실제 방어선은 RLS다.
  CLAUDE.md 금지사항("API KEY 커밋 금지")과 형식적으로 충돌해 확인받았다. 대안이던 "Pages를 아티팩트
  배포로 전환"은 `build_and_commit_site.sh`와 워크플로 9개의 전제를 뒤집는 큰 변경이라 기각.
- **비상 스위치를 뒀다.** `qip_runtime_flags.enabled`를 false로 바꾸면 배포 없이 모든 과금 경로가 즉시
  멈춘다. 코드를 고쳐야만 멈출 수 있는 구조는 사고 시 너무 느리다고 판단했다.

**한계로 합의한 것**(README "알려진 제약"에도 적음):
- PFmanager에 로그인해도 QIP3는 다시 로그인해야 한다. `markias21.github.io`와 `ryugunlee.github.io`는
  서로 다른 출처라 localStorage를 공유하지 않는다 — 브라우저 보안 모델이라 우회 불가. 대안(커스텀 도메인
  하나로 묶기 / 저장소를 같은 계정으로 옮기기)은 비용·URL 변경이 따라 지금은 하지 않는다.
- 미국 종목은 웹 실행 불가(Actions 러너 IP가 EDGAR에 차단). 돈을 쓰고 실패하지 않도록 Edge Function이
  실행 **전에** 막는다.
- 실행 로그 실시간 스트리밍은 하지 않는다. PAT 권한을 넓혀야 해서 안전 원칙과 충돌하므로, 상태
  (대기/진행/성공/실패)와 Actions 링크만 보여준다.

**ES 모듈을 처음 도입했다.** 기존 `static/*.js`는 IIFE인데, 관리자 화면만 모듈로 썼다. 접속 정보
(`config.js`)를 import 해야 하고, PFmanager의 `supabase.js`를 모양 그대로 가져와 두 저장소의 인증
코드를 나란히 비교할 수 있게 하기 위해서다. 공개 페이지 3종은 건드리지 않았다.

구현 위치는 `.claude/STRUCTURE.md`의 "관리자 화면 · 정성 평가 웹 실행" 절 참고.

### (2026-09-16) 정성 평가 운용 — 전 종목 채점 안 함, 주간은 LLM 없이, quick으로 Q7~Q9, 상세 페이지 카드

개발자 방침: "모든 주식에 정성 평가를 돌리지 않는다. 주간 워크플로는 AI 토큰을 쓰지 않는 부분만.
DeepSeek quick으로도 Q7·Q8·Q9를 채우고, 상세 페이지에 등급카드를 표시한다." 질문해 정한 것:
- **주간 작업 범위 = 재판정 + 원문 미리 받기.** 관측값이 있는 종목을 매주 다시 판정해 ★ 플래그·유효기한을
  갱신하고, QIP4 선별 한국 종목 상위 30개(상수)의 사업보고서를 미리 받아 data-store 릴리스에 tar로 보존한다.
  미국은 러너 IP가 EDGAR에 막혀 제외. 워크플로 시크릿은 `DART_API_KEY`뿐 — AI 키를 넣을 경로를 없앴다.
- **III 핵심 주석 슬라이스(`III*`)를 quick 섹션에 추가.** 현금흐름표·자본금·무형자산·재무위험·부문·특수관계자·
  배당 주석은 2.5만 자뿐이라 DeepSeek quick(7.7만 토큰, $0.03)으로도 Q7을 Opus deep과 같은 근거(소각·배당
  원천·손상)로 채웠다(A 85 vs S 95). deep 티어는 이제 "III 전체를 읽어야 할 때"만.
- **등급카드는 근거까지 펼쳐 보여준다.** 종합·배수·★·9항목 칩은 항상, 항목을 펼치면 근거 서술과 인용 2개.
  판정이 어느 티어·모델에서 나왔는지도 표시(`qualitative_grades`에 tier·model 컬럼 추가).
- 근거 서술은 DB에 없어 빌드 시 `qualitative/observations/*.json`(git 추적)을 함께 읽는다. 관측값 JSON이
  git에 있는 것이 표현 계층의 전제가 됐다.
- 카드는 정성 평가를 돌린 종목에만 뜬다. 첫 표시는 Actions에서 `Qualitative Weekly`를 한 번 수동 실행해
  DB에 판정 행이 들어간 뒤(사이트 재빌드 포함).

### (2026-09-16) 삼성전자 파일럿 4회 실측 — Q1 해당 없음, 추정 강도 3단계, DeepSeek 채택

같은 사업보고서를 Sonnet 5 quick($0.25)·DeepSeek flash quick($0.02, 2회)·Opus 5 deep($2.30)으로 채점하고
`qualitative/reports/005930_2026-09-16.md`(+ 아티팩트 페이지)에 비교를 남겼다. 결정:
- **Q1(확정 이익)은 수주형 사업이 아니면 결측 처리.** 개발자가 세 안(결측 / 반복매출 치환 / F 유지) 중
  결측을 골랐다. raw `order_book_business=false`면 판정기가 분모에서 뺀다. Opus 결과는 사람 검토로 반영.
- **추정값은 강도에 따라 다르게.** 개발자가 "얼마나 강한 추정이냐에 따라 다르다"고 해서 raw에 `basis`를
  두었다: disclosed(공시 그대로) / bounded(공시된 상한·하한의 보수적 값 — 인정) / estimated(상한 65).
  Sonnet이 최대 고객을 0.10으로 '감'으로 잡아 S가 되고 DeepSeek이 상한 0.15로 B가 된 차이가 계기.
- **quick 티어 provider는 DeepSeek `deepseek-flash`.** API 모델 목록에 flash·v4-pro 둘뿐이었고, 문서상
  1M 컨텍스트·JSON 출력·입력 $0.30/출력 $1.2. thinking은 기본 켜짐(effort high)이라 quick에서는 끈다.
  근거 품질이 Sonnet과 대등해(인용 전부 원문 일치) 주간 전수 훑기는 이걸로.
- **원본 응답 재검증 명령(`revalidate`)**을 두었다 — 규칙을 고칠 때마다 재호출하면 파일럿이 비싸진다.

  실측하며 출력 스키마를 "공통 항목 1벌의 배열 + raw JSON 문자열"로 바꾸고 사후 검증을 provider 공통으로
  뺐다. 원본 응답을 파일로 남겨 검증 로직을 고쳐도 재호출하지 않게 했다.
- 첫 실측(삼성전자 quick)에서 드러난 규칙 결함: Q6 특수관계자 거래에 연결 종속회사(해외 판매법인)가
  들어가 53%→F가 됐다 → **연결 종속회사 제외**로 정의 수정. 어휘 필터의 "상승세·하락세"가 점유율 서술을
  잡아 제거. Q1(확정 이익)은 수주형이 아닌 사업(메모리·가전)에서 구조적으로 F가 나온다 → 처리 방식은
  개발자 결정 대기(PROBLEMS #37).

### (2026-09-16) 정성 평가 원문 자동 수집 — DART는 섹션 선택, EDGAR는 미검증으로 동봉

첫 실전 추출을 앞두고 개발자가 "사업보고서를 내가 다 캐오는 건 부담스럽다, 자동화 안 되나"라고 물었다.
이 환경에서 접속을 확인하니 OpenDART는 열리고(키 필요) SEC EDGAR는 클라우드 IP를 403으로 막았다.
- **한국은 OpenDART 자동 수집.** 개발자가 무료 키를 발급받아 `.env`의 `DART_API_KEY`로 넣기로 했다
  (FRED/ECOS와 같은 방식). 첫 테스트 종목은 **삼성전자 005930**.
- **사업보고서 전체를 보내지 않는다.** 대형주는 100만 토큰을 넘을 수 있어 기본은 정성 항목이 읽는 대제목
  II·VI·VII·VIII·IX·X·XI만 넣고, III(재무·주석)은 `--sections`로 켤 때만. 원문 60만 자 상한을 두고
  `--force`로만 넘긴다. 이 때문에 첫 실행에서 Q7·Q8·Q9는 결측이 나올 수 있음을 받아들였다.
- **EDGAR 로더는 같이 만들되 미검증으로 둔다.** 로컬 PC에서는 보통 열리므로 코드는 두고, 클라우드 차단은
  우회하지 않는다. SEC가 요구하는 User-Agent(연락처)는 개인정보라 코드에 박지 않고 `EDGAR_USER_AGENT`
  환경변수로 받는다.
- 받은 원문은 `qualitative/sources/<티커>_<접수일>.txt`에 저장하되 git에는 넣지 않는다(수 MB, 공시
  원문 재배포 불필요). 다음 실행은 이 파일을 `extract`에 넘기면 다시 받지 않는다.
- 자동 수집 시 `--asof` 기본값은 오늘이 아니라 **공시 접수일**로 했다 — 관측 기준일은 문서의 날짜다.
- (같은 날 후속) 삼성전자 사업보고서를 실제로 받아 `count_tokens`로 재보니 기본 7섹션이 24.5만 토큰
  (Opus 5 입력 약 $1.2)이었고, 그중 VIII(임원·직원 명단)·IX(계열회사)가 60%를 차지하면서 정성 항목에는
  거의 쓰이지 않았다. 기본을 **I·II·VI·VII·X·XI**(12.3만 토큰, 약 $0.6)로 줄였다. III(재무·주석)을 더하면
  33.5만 토큰(약 $1.7).

### (2026-09-15) 정성 평가를 6축·33항목에서 9항목 0~100점·S~F 체계로 축소

개발자가 두 정성 문서(합계 1,196줄)가 "비상식적으로 길고 쉽지 않아 보인다"고 지적했고, AI도

않다, ② 세분화된 조건이 투자 결정을 완벽하게 만들지 않는다 — 분산투자로 리스크를 나누므로

기업·산업·섹터의 의미와 잠재력(정량과 곁들이기, 섹터 연결 블루오션) / 자기조직화 주의)를 받아
아래를 질문해 결정했다.

### (2026-09-07) QIP4 정량 규칙 체계 신설 — QIP3와 병행, 수집 계층까지 확장

질문하여 답변받은 결정:
- **QIP3를 대체하지 않고 QIP4로 병행 추가** (QIP3 신설 전례와 동일).

  `Market Cap / Close`로 역산해 다음 run까지의 일봉에 적용한다(look-ahead 없음).
  시장·섹터·산업 3단계 전부 산출.
- **12분기 성장 연속성은 하이브리드 자동 승격**: 가용 분기가 16개 미만이면 연간 4개년으로
  판정하고, 누적되어 16분기가 차면 자동으로 원 규칙(12분기)으로 전환. 사용한 기준을
  컬럼에 기록해 화면에 노출한다.
- **안정성 관문 탈락 사유를 상세 페이지에 항목별로 표시한다** — 기존 QIP3는 탈락 사유를
  전혀 보여주지 않고 생존 종목만 노출했다. "판단을 돕는 자료를 충분히 제공한다"는
  프로그램 목표에 맞춰 신규 UI 컴포넌트를 만든다.
- `투자 규칙.md`의 **정량 파트를 전면 재작성**한다(경계조건·시장별 정의 차이·미구현 사유 명시).

### (2026-07-17) 모바일 앱 = Flutter가 아니라 PWA. 표현 계층 언어는 TypeScript 유지
"Flutter로 모바일 앱을 만들고, 웹에 설치 링크를 보여 달라"는 요청에 대해 **PWA(홈 화면에 추가)**로
결정했다. Flutter/Dart는 도입하지 않는다.

그렇게 정한 이유:
- **iOS 설치 링크는 Flutter로도 불가능하다.** 아이폰은 App Store/TestFlight를 거치지 않고 설치할
  방법이 없고 둘 다 Apple Developer Program(연 $99)과 심사가 필요하다. 즉 요청의 핵심인
  "웹 들어가서 링크로 설치"를 Flutter는 안드로이드에서만, PWA는 iOS·안드로이드 양쪽에서 달성한다.
  목적 자체를 PWA가 더 정확히 만족한다.
- 안드로이드 APK 직접 배포도 "출처를 알 수 없는 앱" 허용·Play Protect 경고라는 마찰이 있고,
  스토어 등록은 비용·심사·신원확인이 따른다.
- 백엔드 서버가 없어 앱을 만들어도 결국 GitHub Pages의 정적 JSON을 읽는 구조가 된다. 그러면
  웹과 정보 신선도가 같으므로 네이티브의 이점이 크지 않다.
- **CLAUDE.md "데이터 표현 영역은 TypeScript 예정"과 Dart가 충돌**한다. 이 충돌을 질문했고,
  개발자가 "TypeScript 유지(PWA)"를 택했다. 표현 계층 언어를 Python(Jinja)+TS+Dart 셋으로
  늘리지 않는다.

이 선택의 큰 이점: PWA는 **사이트 자체가 앱**이라 앱 전용 코드도, 앱용 JSON API도 없다. 그래서
"앱이 다룰 데이터 범위 = 웹과 동일 전부"(질문에 대한 개발자 답변)가 추가 작업 없이 자동 충족되고,
표현 계층을 고치면 설치된 앱도 그대로 따라 바뀐다. 유지보수 대상이 하나로 유지된다.

한계(알고 선택한 것): 푸시 알림(iOS 제약 큼)·스토어 노출·네이티브 성능은 포기한다. 나중에 이것들이
정말 필요해지면 그때 다시 판단한다 — PWA를 넣었다고 앱 개발이 막히지는 않는다.

구현은 `presentation/builders/pwa.py` + `templates/{manifest.webmanifest,sw.js}.jinja` +
`static/{install,sw-register}.js` (STRUCTURE.md 참고).

### (2026-09-21) Q8 집중도를 채점에서 빼 "다각화 정도" 표시 항목으로, Q9는 매크로 실측 지표로

예외를 쓰고 있다. 시장 지수를 먼저 통제해 시장 전체의 등락은 걷어낸다.

**정세·관세는 프록시로 대체했다.** 전쟁·지정학 정세는 수치 시계열 소스가 없고, 뉴스 기반 판정은
재현성이 없어 "실증적"이라는 요구와 반대가 된다. 이미 수집 중인 VIX·국제 금(위험회피 수요)과
유가로 "정세가 시장에 남긴 흔적"을 대신 측정한다. 관세율도 시계열이 없어 지역별 매출 비중(공시)과
해당 통화 민감도로 간접 측정한다.

**감점은 조건 중첩 시에만(선택지 중 1안).** 민감도가 크다는 것 자체는 좋고 나쁨이 아니다 —
정유사의 유가 민감도는 본업이지 취약성이 아니다. 그래서 단일 국가 집중 ≥50% **AND** 미헤지
**AND** 유의한 요인 노출, 셋이 겹칠 때만 깎는다(요인당 5점, 최대 15점). 나머지는 전부 표시만 한다.
덧붙여 **헤지했다고 공시했는데 환율에 유의하게 연동되는 경우**를 표시 전용 신호로 넣었다 —
공시와 실측이 어긋난 지점이라 확인 가치가 가장 크지만, 헤지 회계·시점 차이로도 생길 수 있어
감점 근거로는 쓰지 않는다.

**남긴 것**: 앞서 지적한 "국내 생산 100% + 환헤지 완료 = Q9 20점(F)" 과벌점은 이번에 고치지
않았다(선택되지 않은 안). `PROBLEMS.md` 41번에 기록했다.

## 2026-09-22 — QIP4 정량 기준 미반영 조사와 복소수 방어선

**배경.** "미국·한국 둘 다 만들어둔 정량 평가 기준이 안 쓰이는 것 같다"는 지적으로 조사했다.
확인 결과 QIP4(`.claude/투자 규칙.md`의 정량적 평가 기준)는 **한 번도 DB에 반영된 적이 없었다**
(경위와 근거는 `PROBLEMS.md` #40).

**결정 1 — 근본 원인은 계산 쪽에서 고친다.** `_revenue_cagr`에 `revenues[-1] <= 0` 가드를 넣어
결측(None)으로 낸다. "매출이 음수인 기업의 연평균 성장률"은 정의되지 않는 값이라 0이나 임의의
대체값을 넣는 것보다 결측이 옳다. `qip4_gate`의 밸류트랩 판정(`Revenue CAGR < 0`)은 결측이면
보정을 걸지 않으므로 하류 영향이 없다.

**결정 2 — 저장 경계에 안전망을 함께 둔다(사용자 허가받음).** 계산 쪽만 고치면 앞으로 다른
계산에서 같은 사고가 날 때 또 몇 시간짜리 수집이 통째로 죽는다. `save_snapshot_factors`/
`update_snapshot_scores` 진입부에서 복소수 컬럼을 실수로 정규화한다(허수부가 있으면 결측 + 경고 출력).
**조용히 넘어가지 않고 경고를 찍는 것**이 핵심 — 방어선이 계산 버그를 가리면 안 되기 때문이다.
기존 중복 티커 방어선(#30)과 같은 성격이라 새 설계를 도입하는 것이 아니다.

**결정 3 — 사이트 커밋 rebase 충돌(D)은 분리한다.** 원인(동시 워크플로의 docs/ 충돌)이 완전히
달라 같은 커밋에 묶지 않는다. QIP4 재수집이 끝난 뒤 따로 진행한다.

**보류.** QIP4 값을 사이트에 띄우려면 재수집이 필요하다(QIP4 원천 컬럼은 수집 단계에서 채워지므로
`compute_scores.py` 재점수만으로는 안 된다). 사용자 요청으로 수정 후 4개 시장 워크플로를 직접 실행한다.
